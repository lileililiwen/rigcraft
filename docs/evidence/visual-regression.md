# Visual regression baseline

`e2e/visual.spec.ts` compares twelve committed screenshots of the six client
routes with Playwright's `toHaveScreenshot()`. The baselines are captured from
the production bundle the Rust service serves, with the data the browser suite
seeds, at a fixed desktop and phone viewport. This document records the baseline
set, the exact commands, the determinism proof, the mutation that fails, the
restored pass and the masked values.

## Determinism

The visual tests seed their own state immediately before the capture, so the
order of spec files does not matter:

- `/inventory`, `/builds/check`, `/recommend` and `/diagnose` commit the shipped
  sample through `seedSample`. A fresh import is always revision 1
  (`snapshot_from_preview`), so the revision in the console bar, the report
  metadata and the snapshot `<select>` is the same on every run even though the
  database accumulates snapshots.
- `/catalog` removes every stored dataset through
  `DELETE /api/catalog/datasets/{id}?confirm=remove`, then uploads the same
  synthetic fixture the catalog journeys use. Removing a dataset cascades only
  to its own parts; inventory and snapshots are untouched. The registry is one
  three-part dataset on the first and on a repeat run.
- `/nope` is a plain `text/plain` 404 document with no application state.

`threshold` is `0.05` and `maxDiffPixelRatio` is `0.01`, with
`animations: 'disabled'`, `caret: 'hide'`, `deviceScaleFactor: 1`,
`locale: en-US` and `timezoneId: UTC`. The ratio absorbs a stray antialiased
glyph edge; it does not absorb a colour or spacing change. Identical renders on
the same host are bit-identical.

Two runs against **one** service and **one** SQLite file, with no reset between
them:

```sh
# the service was started once on 127.0.0.1:33272 with
# RIGCRAFT_DATA_DIR=/tmp/opencode/visual-db2
npx playwright test --config=test-results/persistent.config.ts e2e/visual.spec.ts
npx playwright test --config=test-results/persistent.config.ts e2e/visual.spec.ts
```

- Run 1: `12 passed (7.9s)` — this run created the sample snapshots and the
  catalog dataset.
- Run 2: `12 passed (5.7s)` — this run saw the snapshots and datasets from run 1
  and re-seeded on top of them; every baseline still matched.

The full declared suite also passes on a fresh database **with the visual spec
included**, so the baselines generated by the visual spec alone still match after
the catalog, compatibility, diagnosis, inventory, portability, recommendation,
regression and shell specs have run:

```sh
npm run test:e2e
# 40 passed (30.9s)
```

## The masked values

Masks are Playwright locators over block-level containers; the pixel tolerance is
not used to hide a dynamic value.

| Route | Masked locator | Why |
| --- | --- | --- |
| `/inventory` | `section.console-bar .console-stats > div` (first) | revision cell |
| `/inventory` | `section.console-bar .console-bar__meta` | committed timestamp |
| `/inventory` | `dl.record-meta > div` for `Snapshot ID` | generated snapshot id |
| `/inventory` | `dl.record-meta > div` for `Committed` | committed timestamp |
| `/inventory` | `dl.record-meta > div` for `Source file` | sha256 fragment |
| `/catalog` | registry `td[data-label="Dataset"]` | dataset import timestamp |
| `/catalog` | `#catalog-file` | native control label, supplied by the browser |
| `/builds/check` | `.console-summary .verdict-line > span.small.muted` | checked timestamp, snapshot revision, rule set |
| `/builds/check` | every `time` | catalogue provenance observed-at (recorded at import) |
| `/builds/check` | `#check-snapshot` | snapshot `<select>` label embeds a timestamp and short id |
| `/recommend` | `article.candidate > p.small.muted` | check report id and snapshot revision |
| `/recommend` | comparison table `Check report` row | check report id |
| `/recommend` | `#recommend-snapshot` | snapshot `<select>` label |

| `/diagnose` | every `time` | catalogue provenance observed-at |

The snapshot `<select>` is above the result anchor and therefore outside the
captured viewport at both widths; it is masked as well so the label is covered
wherever the capture lands.

## A one-token mutation fails

The proof changes one brand surface token, rebuilds and runs only the visual
spec. `--brand-carbon-950`, the page background, was moved from `#0a1224` to
`#2a1244` in `apps/web/src/styles/brand.css`; nothing else changed.

```sh
npm run build
# dist/assets/index-BYGfIe8C.css  27.70 kB
npm run test:e2e -- e2e/visual.spec.ts
# exit 1; 10 failed, 2 passed
```

The two 404 baselines pass because a `text/plain` document does not use the
brand token at all. The ten application baselines fail:

| Test | Differing pixels | Ratio |
| --- | --- | --- |
| inventory 1440×900 | 240,654 | 0.19 |
| catalog 1440×900 | 299,130 | 0.24 |
| build check 1440×900 | 201,600 | 0.16 |
| recommend 1440×900 | 74,226 | 0.06 |
| diagnose 1440×900 | 201,600 | 0.16 |
| inventory 390×844 | 38,606 | 0.12 |
| catalog 390×844 | 38,578 | 0.12 |
| build check 390×844 | 27,014 | 0.09 |
| recommend 390×844 | 35,742 | 0.11 |
| diagnose 390×844 | 27,014 | 0.09 |

Every failing test writes an expected, actual and diff image into its output
directory, for example:

```
test-results/visual-visual-baseline-at-1440x900-diagnose-at-1440x900-chromium/
  diagnose-1440x900-actual.png
  diagnose-1440x900-diff.png
```

The listener reports, for that test, `201600 pixels (ratio 0.16 of all image
pixels) are different` and names the snapshot `diagnose-1440x900.png`.

This mutation is deliberately subtle. With Playwright's default `threshold: 0.2`
it **passed**, because the colour distance between the two dark backgrounds is
below that bound; with `threshold: 0.05` it fails on all ten application routes.
That is why the committed threshold is stricter than the default.

## The restored pass

The token was restored to `#0a1224`, `apps/web/src/styles/brand.css` has no diff,
and `npm run build` again emitted `index-B-c8V-0n.css` (27,698 bytes) and
`index-DO5RYnOJ.js` (307,491 bytes). `npm run test:e2e` then reported
`40 passed (30.9s)`, and the same-database pair above passed at `12 passed
(7.9s)` / `12 passed (5.7s)`. The baseline files were not regenerated after the
mutation, so they are the original bytes listed above.

## Updating the baselines

```sh
npm run test:e2e -- --update-snapshots
```

`e2e/run.mjs` forwards the arguments to the Playwright CLI, so this is the one
deliberate update command. Regenerating is legitimate only when:

- the visual change is intended;
- a human reviewed the new images (a diff is not approval by itself);
- the new images are committed in the same change as the code that caused them.

A changed pixel that fails the suite during unrelated work is a regression to
investigate, not a reason to run the update command.

## Platform

The committed set was generated on **Linux x86_64** (`7.0.0-38-generic`) with
**Google Chrome 154.0.8037.97**, the `chromium` Playwright project and
`channel: 'chrome'`. The file names carry the `-chromium-linux` suffix that
Playwright derives from the project and platform. The system font stack
(`system-ui`/`ui-monospace`, no webfont) resolves to the host's fonts, so a
different OS, GPU or font stack renders different pixels and needs its own
baseline set. The baselines are not portable and this document does not claim
they are.
